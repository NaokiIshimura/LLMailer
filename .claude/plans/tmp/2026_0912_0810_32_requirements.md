# LLMailer 要件定義書

## 1. 概要

LLMailer は「メーラー」のUIメタファーを用いて LLM（Claude）に指示を送るためのアプリケーションである。
チャットUIではなく、受信箱・スレッド・作成画面を持つメールクライアントの操作感で LLM とやりとりする。

| メールの概念 | LLMailer での意味 |
| --- | --- |
| 宛先（To） | 指示を送る AI エージェント（モデル＋システムプロンプトの組） |
| 件名（Subject） | スレッドのお題。会話の単位 |
| 本文（Body） | LLM への指示 |
| 返信 | LLM からの応答 |
| スレッド | LLM の会話履歴 |
| アドレス帳 | エージェント定義一覧 |
| 配信失敗通知 | API 呼び出しエラー |

### 採用方針（確定事項）

- 送受信方式: **アプリ内メッセージ**（SMTP/IMAP は使わない。ただし送受信は差し替え可能な層として設計する）
- 技術スタック: **Next.js（App Router）+ TypeScript**
- LLM: **Claude API（`claude-opus-5`）**
- 永続化: **JSON ファイル**（`data/` 配下）

## 2. 機能要件

| ID | 機能 | 内容 | 優先度 |
| --- | --- | --- | --- |
| FR-01 | 3ペインのメーラーUI | サイドバー（フォルダ／アドレス帳）、スレッド一覧、スレッド本文の3ペイン構成 | 必須 |
| FR-02 | フォルダ表示 | 受信箱 / 送信済み / 下書き / 全件 の切り替え | 必須 |
| FR-03 | メッセージ作成・送信 | To（複数可）・件名・本文を入力して送信 | 必須 |
| FR-04 | LLM への指示配信 | 送信されたメッセージを宛先エージェントの設定（モデル・システムプロンプト）で Claude API へ送り、応答を受信メッセージとして保存 | 必須 |
| FR-05 | 複数宛先への同時送信 | To に複数エージェントを指定した場合、各エージェントから個別に返信が届く | 必須 |
| FR-06 | スレッド内返信 | 同一スレッド内で返信すると、それまでの会話履歴を LLM に引き継ぐ | 必須 |
| FR-07 | アドレス帳 | エージェント一覧の表示と、作成画面からの宛先選択 | 必須 |
| FR-08 | 未読管理 | 受信メッセージの未読／既読。スレッド一覧に未読件数を表示 | 必須 |
| FR-09 | ローディング表示 | API リクエスト中はローダーを表示し、成功・失敗いずれでも非表示にする。複数リクエストが並行する場合は全完了まで表示 | 必須 |
| FR-10 | 配信状態の可視化 | メッセージごとに `送信済み` / `配信中` / `受信` / `配信失敗` を表示 | 必須 |
| FR-11 | エラーハンドリング | Claude API 失敗時はスレッドに「配信失敗通知」としてエラー内容を残す。`stop_reason: "refusal"` も同様に扱う | 必須 |
| FR-12 | 下書き保存 | 作成途中のメッセージを下書きとして保存し、再開できる | 推奨 |
| FR-13 | 検索 | 件名・本文の全文検索（部分一致） | 推奨 |
| FR-14 | エージェントのCRUD | UI からエージェント（モデル・システムプロンプト）を追加・編集 | 任意 |
| FR-15 | ストリーミング受信 | 応答を逐次表示する（SSE） | 将来 |
| FR-16 | 実メール連携 | IMAP/SMTP アダプタによる実メール送受信 | 将来（スコープ外） |
| FR-17 | 添付ファイル | 画像・PDF を添付して LLM に渡す | 将来（スコープ外） |

## 3. 非機能要件

| ID | 分類 | 内容 |
| --- | --- | --- |
| NFR-01 | 実行環境 | ローカル起動（`npm run dev`）。単一ユーザー・単一プロセス前提 |
| NFR-02 | 認証 | なし（ローカル利用のため）。将来の多ユーザー化は考慮外 |
| NFR-03 | 秘密情報 | `ANTHROPIC_API_KEY` は環境変数から読む。クライアントへ渡さない |
| NFR-04 | 永続化 | `data/*.json`。書き込みは直列化して破損を防ぐ |
| NFR-05 | 言語 | UI・コメント・ドキュメントは日本語 |
| NFR-06 | 型安全 | TypeScript strict。Anthropic SDK の型をそのまま利用し、独自の重複型を定義しない |
| NFR-07 | 構成 | ロジック（hooks）と UI（components）を分離し、1ファイルに集約しない |
| NFR-08 | 応答性 | LLM 応答待ちの間も UI 操作（他スレッド閲覧）が可能であること |

## 4. ユースケース

### UC-01 エージェントに指示を送る
1. ユーザーが「作成」をクリックする
2. 宛先にエージェント（例: `opus@llmailer.local`）を選ぶ
3. 件名「リリースノートの要約」、本文に指示を書く
4. 送信すると、送信済みに記録され、スレッドに `配信中` のプレースホルダが並ぶ
5. 応答が届くと受信箱に未読として現れる

### UC-02 複数エージェントに同じ指示を送る
1. 宛先に `opus@llmailer.local` と `haiku@llmailer.local` を指定して送信
2. 各エージェントから個別の返信がスレッドに届き、応答を並べて比較できる

### UC-03 スレッドで議論を続ける
1. 受信した返信を開き「返信」する
2. これまでのスレッドの往復が会話履歴として LLM に渡り、文脈を保った応答が返る

### UC-04 配信失敗を確認する
1. API キー未設定などで送信する
2. スレッドに「配信失敗通知」が残り、原因が読める
3. 原因を解消して再送できる

## 5. 受け入れ基準

- [ ] AC-01 `npm run dev` で起動し、3ペインのメーラーUIが表示される
- [ ] AC-02 作成画面から送信すると、Claude の応答が受信メッセージとしてスレッドに追加される
- [ ] AC-03 複数宛先に送信すると、宛先と同数の返信が届く
- [ ] AC-04 スレッド内で返信すると、過去の往復を踏まえた応答が返る
- [ ] AC-05 送信中はローダーが表示され、成功・失敗いずれでも消える
- [ ] AC-06 `ANTHROPIC_API_KEY` 未設定時に配信失敗通知が表示され、アプリはクラッシュしない
- [ ] AC-07 リロード後もスレッド・メッセージが保持されている
- [ ] AC-08 未読件数が表示され、スレッドを開くと既読になる

---

## 6. 制約事項

- C-01 SMTP/IMAP は使わない。ただし配信処理は `Transport` インターフェース越しに呼び出し、後から実メールへ差し替えられる形にする
- C-02 JSON ファイル永続化のため、同時書き込み耐性は単一プロセス前提の簡易実装にとどめる
- C-03 Claude API のモデルは `claude-opus-5` を既定とする（エージェント単位で変更可）
- C-04 添付ファイル・ストリーミングは初期スコープに含めない
